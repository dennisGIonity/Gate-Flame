# The product, re-stated by Dennis on 2026-10-03

This supersedes the "The product IS the kiosk" framing in `CLAUDE.md` and every earlier
pin. Two models go to launch. Nothing else is built until these two are launch-ready.

## Standard T3 — the box, the app, the fleet

In Dennis's words: *"kiosk = only there is a display ui on the device is so that the user
can connect the device to their wifi router, from there anything else is well nice but
useless, seeing as once the phone is paired via the apk all stats and minor choices like
vpn set to usa or no porn on devices a b and c … so connecting + pairing + providing the
data that gets generated by the background functions from the device functions/reporting
+ rest just to show some niceties. so user will basically setup once there after only
look and set this and that from the synced apk."*

So, in order of what matters:

1. **The screen on the box is SETUP.** Connect the box to the household network (Wi-Fi
   list + password, or "connected by cable"), show the box's address, show the one
   router step ADR-001 needs ("point your router's DNS at this address") with a live
   read-back of whether the router is doing it, then pair the phone (6-digit code).
   After that the screen shows a status face. Everything else on it is a nicety.
2. **The box's job after setup is background work:** filter DNS (Pi-hole + Unbound),
   watch itself (watchdog, bypass, self-heal), keep history, report health to the fleet.
3. **The phone app is where the customer lives:** every number, every setting (threat
   level, categories, pause, Shield per device, device names), health, history, and
   Ionibot as the instruction manual.
4. **The fleet console is the billable surface.** Boxes report in; support reads.

**One hard limit, stated now so nobody designs around it by accident:** *"no porn on
devices a, b and c"* is **per-device filtering**, and the Standard T3 box cannot do it.
ADR-001 has the router forward DNS to the box, so Pi-hole sees one client — the router.
Content categories on Standard T3 are **household-wide**. Per-device rules need the box
to see each device's queries, which means devices pointed at the box directly (the
model ADR-001 rejected on load-shedding grounds) or an in-path box (Premium T3's open
question). This is not re-litigated here; it is written down so the app never promises
per-device categories. Shield IS per device, because each phone installs its own
profile — that is a different mechanism and stays.

## T1 — the ESP32 that connects, and a server that does everything else

In Dennis's words: *"the tier 1 mcp version will in fact be alot different ALOT more
reporting with no real other functions other than connection, there on forth reporting
and main functions will reside with the mcp server itself."*

So: the device **connects** (joins the household Wi-Fi, takes the router's forwarded DNS
queries, answers from a signed Bloom filter, forwards the rest) and **reports** (counters
only — no domain ever leaves the board). Lists, the dashboard, alerts, the MCP tools,
OTA, support — all on the Ionity server. T1 has no screen and no app of its own in v1;
the server's dashboard and MCP are its face.
